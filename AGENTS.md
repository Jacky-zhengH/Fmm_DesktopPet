# fmm project workflow

- Preserve the private GitHub repository `Jacky-zhengH/Fmm_DesktopPet`; do not change visibility.
- Keep `main` as the tested baseline. Subsequent runtime changes use a focused branch, associated Issue and PR. In addition to `fix/`, `feat/`, or `phase/`, user-named version branches such as `ver0.1.0` are allowed.
- Version families follow the user's stages: first stage is `0.1.x`, next stage is `0.2.x`. The user alone decides when to enter `1.0.x`. A branch named `ver0.1.0` is distinct from the existing immutable `v0.1.0` tag; do not recreate a tag or publish a release without acceptance.
- Commit completed units with clear messages; never force-push shared history or rewrite accepted release tags.
- Push a tested checkpoint after each meaningful unit or substantial set of code changes, before continuing the next large change. Keep small related edits together. For longer work, create incremental commits and pushes on the focused branch instead of waiting until the entire stage is finished. Merge into main only after the required checks pass; clean up completed branches while preserving commits and existing tags.
- Each accepted stage has an annotated version tag, CHANGELOG entry and validation notes. Tagging is done after required tests and user acceptance, not merely because a milestone exists.
- Before changing runtime behavior, establish a clean checkpoint for existing user changes. Do not discard unrelated changes.
- The common manual test entry is the root `run.bat`. The old portable EXE is a preserved local artifact.
- Run `.venv/Scripts/python.exe -m unittest discover -s tests -v` for relevant runtime changes. On CI use the selected Python interpreter directly. The retired `deskpet/deskpet` forwarding layer is removed.
- Keep `.venv`, `.user`, logs, credentials, build output and desktop screenshots out of Git. Keep source PNGs and intentionally provided character references versioned.
- Do not modify original character art while fixing layout math. Asset changes require explicit before/after visual review.
- Record planned work separately from implemented behavior; update README/roadmap when the implementation changes.
- For simple manual operations such as opening Photoshop or importing working images, provide concise text instructions instead of creating extra BAT files or launchers. Preserve the established root run.bat / setup.bat workflow.

- Release titles and portable package names use `Fmm-DesktopPet-vx.x.x`; annotated Git tags keep `vx.x.x`. Read the version from `app/pet/version.py`. The original portable EXE and source ZIP are preserved in ignored `.local/original/`.
- Each release ships a committed-source ZIP and an EXE portable ZIP, both with the current simple feature guide (`docs/QUICK_GUIDE.md`), plus a standalone EXE, guide and checksums. Keep source and EXE tied to the same saved source tree.
- Maintain version-specific `docs/releases/x.x.x.md` with current features, changes and download instructions; use it as the release body. Keep the hidden seasonal greeting out of user guides, feature lists and release notes.
- Develop and publish only the standard user build. The user retired the active ForFmm installation and source worktree; do not recreate them. Preserve existing historical tags for rollback; never push local custom refs or historical custom code into the standard repository.
- Canonical source directories are `app/`, `tests/`, `tools/`, `requirements/`, `docs/`, and `image/`. Standard packages live in ignored `versions/user/`; source settings live in `.local/profiles/user-source/`, portable settings beside the EXE. Do not recreate the retired `deskpet/`, `dist/`, root `analysis/`, `versions/fmm/`, or `.local/for-fmm-source/` directories. Keep current art audit data beside art in `image/review/<version>/audit/` and repair provenance in `image/repaired/<version>/processing.json`.
- Keep developer commands under `tools/release/`, `tools/github/`, and `tools/diagnostics/`; do not recreate the retired root `scripts/` directory. Release packaging uses `tools/release/package_release.py`.
- Keep art references in `image/references/`, review candidates in `image/repaired/<version>/`, and local PSD/manual work in ignored `image/work/<version>/`. Runtime art stays in `app/assets/sprites/` until visual acceptance. All comparison/preview images go in `image/review/<version>/`; keep one final comparison sheet and a necessary animation preview per revision rather than piles of intermediate images.
- Explain routine questions in chat. Maintain existing guides and one plan per stage; do not generate a new Markdown file for each answer. Remove superseded duplicate documents/previews after preserving any unique information; use Git history for old tracked versions. Delete disposable experiments and old intermediate packages rather than accumulating archives. Build caches belong in `.local/build/`; retain only necessary original art-generation outputs in `.local/art/`.
