# 下一阶段建议（规划，尚未实现）

建议顺序：互动动画与动作管理 → 小规模养成 → 音乐与直播连接。先沿用 Python / PySide6，暂不更换整个技术栈，也不把所有需求同时塞进现有界面。

## 先补互动动画

目前 Character 的主要状态是待机、走路、睡眠、开心和拖动，现有行走只有两帧。素材库支持帧序列、帧率、循环、朝向和关闭额外程序动效；新动作仍需要触发、优先级和结束方式，放入图片不会自动形成新互动。

第一批建议做拖动时拎起和轻晃、连续点击后的不满表情、靠近边缘的探头。先把每个动作的统一画布、人物比例、脚底位置、透明背景和退出规则定下来，再补帧。睡眠和眨眼目前共用画面，也可在这一批分开补。

配套增加动作协调器：拖动能打断演出，定时提醒不与进食等动作抢控制，动作结束后能恢复正确状态。`BubbleUI` 同时负责面板、对话和计时，后续应逐项拆出控制器，界面只负责显示；本次只整理目录，没有进行这层行为拆分。

已有 Qt 属性动画用于移动和轮播，可以沿用。状态增多后可评估 Qt 状态机，但不必为几个新动作先引入一个重框架。[Qt 状态与动画说明](https://doc.qt.io/qtforpython-6/overviews/qtstatemachine-cpp-guide.html)

验收重点：动作切换不变大变小、不跳脚底；在屏幕边角不裁切；拖动/睡眠/提醒之间能正确恢复；普通版与本地定制版保持分开。

## 再把喂食做成小系统

当前数值只在面板里演示，没有存档。第一版只做心情、饱食、投喂间隔和少量对应台词，处理数值边界、退出重开及离线时间；不急着增加复杂经济和商店。已有轮播界面可以继续使用。

报时作为可开关的独立服务，默认不打断睡眠，不依附面板是否打开。与计时提醒共用动作协调器，避免多处直接修改角色状态。

## 最后接音乐与直播

音乐先验证“读取当前曲目/播放状态”与暂停/继续，再考虑播放器专属适配。Windows 提供系统媒体会话接口；具体 QQ 音乐、网易云音乐版本是否暴露会话，需要实机验证，不能提前保证全兼容。[Microsoft 媒体会话接口](https://learn.microsoft.com/en-us/uwp/api/windows.media.control.globalsystemmediatransportcontrolssessionmanager.requestasync?view=winrt-26100)

直播先做保存房间链接和一键进入，随后再单独验证状态获取、合理请求频率、网络失败与通知规则。网络请求放在独立服务中，不阻塞 Qt 界面，不在 UI 上堆平台接入细节。
